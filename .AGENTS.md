# LexHarness Project Norms & Agent Guidelines

## 1. Product & UX Norms ("Speak Lawyer, Never Engineer")
- **Practitioner Terminology Only**: Use legal practice terminology in all UI, docs, and README copy (*Matters*, *Active / Settled*, *Peer Review*, *Citation & Record Auditor*, *Opposing Counsel Review*, *Exhibits & Authorities*, *Draft & Redlines*).
- **Zero SWE / AI Jargon ("No Nerd-isms")**: Never expose terms like *threads*, *branches*, *commits*, *diffs*, *ONNX*, *logits*, *telemetry*, or *harness* in the main user interface.
- **Brand Name**: Always refer to the application as **LexHarness** (never "Free Legal Assist", which is only the GitHub repository slug).
- **Calm, Uncluttered Chrome**: Keep the 3-pane workspace quiet and document-centric. Avoid duplicate action buttons, redundant gear icons, or persistent banners; tuck advanced controls into Settings or collapsible drawers.

## 2. Legal Grounding, Routing & Data Isolation
- **Strict Sample-Matter Isolation**: Hardcoded demo/tutorial templates (*Marcus Thorne*, *Apex Biometrics*, *John Doe*) are strictly gated to their specific sample matter IDs. User-created matters must ground drafts, redlines, and peer reviews **only** in that matter's uploaded corpus and active profile/jurisdiction.
- **Always Update Both the Desktop & Web Tutorials Together**: Whenever features or UX change, you **must** update:
  1. The in-app Guided Tour ([TutorialOverlay.tsx](src/renderer/components/TutorialOverlay.tsx)) and sample casework ([tutorialSampleCase.ts](src/main/db/tutorialSampleCase.ts)), including `openDialog` states for any off-main-screen modals (such as Settings or Connect Agents).
  2. The GitHub Pages Interactive Web Tutorial & Live Workspace Simulator ([docs/index.html](docs/index.html), served at `https://bentito.github.io/free-legal-assist/#tour` and linked from [README.md](README.md)), keeping `WEB_TOUR_STEPS` and all simulated `#tour-*` DOM spotlight targets 100% synchronized with `TOUR_STEPS` in `TutorialOverlay.tsx`.
  3. The automated tutorial parity test in [legalHarness.test.ts](src/main/__tests__/legalHarness.test.ts) so CI/pre-flight checks fail if the desktop tour and web tour ever drift out of sync.
- **Never Downgrade Substantive Drafting**: Prompts that ask to *draft*, *write*, *redline*, *revise*, or *prepare* a pleading, motion, complaint, or brief must stay on `FRONTIER_REASONING` (preserving the user's chosen frontier model) rather than routing to `FAST_ECONOMY`.
- **Agent-Native MCP Separation**: MCP servers (e.g., CourtListener) run natively inside the user's CLI agents (`codex`, `claude`, `agy`). LexHarness only handles baseline config assurance and `safeStorage` token sync, while owning local matter corpus tools and PII scrubbing.

## 3. Technical & Packaging Guardrails
- **Zero-Dependency Cross-Compilation**: Prefer built-in Node/Electron primitives (`node:zlib`, pure-TS parsers, `sql.js`) over native C++ addons or external daemons (no Python/OCR installs) so macOS (`arm64`) and Windows (`x64`/`arm64`) installers cross-compile cleanly on macOS.
- **macOS TCC Sandboxing**: Keep CLI agent scratch/working directories inside `<userData>`—never spawn child processes in `~`, `~/Documents`, or `~/Downloads` where macOS will prompt for folder permissions.
- **Windows NSIS Compatibility**: Preserve the custom `build/installer.nsh` recovery macros and `verifyUpdateCodeSignature: false` so upgrades over older installs never fail on Windows.

## 4. Git, Versioning, PR & Release Workflow
- **Semantic Versioning (SemVer)**: Follow SemVer (`vX.Y.Z`) for all versioning logic—bump `Z` (patch) for backwards-compatible bug fixes, `Y` (minor) for new backwards-compatible features/capabilities, and `X` (major) for breaking changes or major milestones.
- **Fork → Upstream PR Flow**: Push feature/fix branches to `origin` (`bentitopolis/free-legal-assist`) and open PRs targeting `upstream` (`bentito/free-legal-assist`).
- **Expand Test Coverage for Every Feature or Bug Fix**: Every feature, UX/workflow change, or bug fix must be accompanied by new or expanded unit and integration tests in `src/main/__tests__/` verifying both the feature/fix and tutorial coverage.
- **Pre-Flight Checks**: Always run `npm run typecheck && npm test` before opening a PR or cutting a release.
- **Release Checklist (`vX.Y.Z`)**:
  1. Bump the version in `package.json`, `README.md` installer links, and `docs/index.html` together.
  2. Build both platforms (`npm run dist:mac && npm run dist:win`).
  3. Commit, tag `vX.Y.Z`, and push `main` + tags to both `upstream` and `origin`.
  4. Publish the GitHub release on `upstream` with all 5 binaries attached (`-arm64.dmg`, `-arm64-mac.zip`, `.Setup.X.Y.Z.exe`, `-win.zip`, `-arm64-win.zip`).
